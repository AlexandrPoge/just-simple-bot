# Архитектура приложения

## 1. Назначение

Прототип предназначен для автоматизации первой линии сервисной поддержки в Telegram. Он должен сокращать количество повторяющихся вопросов, сохранять единый официальный стиль ответов и не создавать технические инструкции из общих знаний модели.

## 2. Границы MVP

Входит в MVP:

- приём текстовых сообщений Telegram;
- команды `/start` и `/help`;
- нормализация вопроса;
- поиск подходящей статьи в базе знаний;
- выдача готового ответа;
- безопасный fallback при отсутствии информации;
- регистрация неизвестных вопросов;
- перезагрузка базы знаний без изменения бизнес-логики;
- автоматические тесты сценариев.

Не входит в MVP:

- полноценная CRM;
- личный кабинет клиента;
- самостоятельная генерация инструкций;
- голосовые сообщения;
- обработка изображений и документов;
- сложная админ-панель;
- автоматическое принятие решений по аварийным ситуациям.

## 3. Логическая схема

```text
Пользователь Telegram
        |
        v
Telegram Bot Adapter
        |
        v
Message Handler
        |
        v
Question Normalizer
        |
        v
Knowledge Search Service
        |
        +--> Confidence Gate -- достаточная уверенность --> Answer Renderer
        |                                                     |
        |                                                     v
        |                                               Telegram Response
        |
        +--> недостаточная уверенность --> Escalation Service
                                              |
                                              +--> Fallback клиенту
                                              +--> журнал сервисного отдела
```

## 4. Компоненты

### Telegram Bot Adapter

Отвечает только за интеграцию с Telegram:

- получение updates через polling или webhook;
- извлечение текста и идентификатора пользователя;
- отправка сообщений;
- обработка ошибок Telegram API.

Бизнес-правила не должны находиться в этом компоненте.

### Message Handler

Оркестрирует обработку одного пользовательского сообщения:

1. проверяет тип сообщения;
2. передаёт текст нормализатору;
3. вызывает поиск;
4. передаёт результат в confidence gate;
5. отправляет ответ или запускает эскалацию;
6. записывает результат обработки.

### Question Normalizer

Подготавливает вопрос к поиску:

- переводит текст в нижний регистр;
- удаляет лишнюю пунктуацию;
- нормализует пробелы;
- обрабатывает распространённые сокращения и варианты написания;
- не меняет смысл пользовательского текста.

### Knowledge Repository

Загружает статьи из отдельного файла или хранилища. Репозиторий не формирует ответы и не добавляет новые факты.

Начальная реализация хранения: YAML-файл в репозитории. Дальнейшие варианты: Google Sheets, PostgreSQL или CMS базы знаний.

### Knowledge Search Service

Ищет наиболее подходящую статью по заголовку, ключевым словам и примерам вопросов.

Стратегия поиска:

1. точное совпадение сущности оборудования;
2. совпадение ключевых слов;
3. совпадение с примерами формулировок;
4. при расширении базы — семантический поиск по embeddings;
5. возврат статьи вместе с оценкой и объяснением совпадения.

### Confidence Gate

Защищает систему от ложных совпадений. Проверяет:

- минимальный общий score;
- наличие обязательной сущности оборудования;
- отсутствие противоречий между найденными статьями;
- разницу между первым и вторым результатом.

Если условия не выполнены, результат считается неизвестным.

### Answer Renderer

Возвращает только утверждённое поле `answer` найденной статьи. Компонент не перефразирует, не дополняет и не сокращает технические инструкции.

### Escalation Service

Обрабатывает вопросы, на которые нельзя безопасно ответить:

- отправляет клиенту fallback-сообщение;
- сохраняет вопрос в журнале;
- помечает запись статусом `needs_human`;
- в следующей версии может отправлять вопрос в рабочий Telegram-чат, Google Таблицу или CRM.

### Audit Logger

Фиксирует:

- время и идентификатор запроса;
- текст вопроса;
- найденную статью;
- score;
- тип результата: `answered`, `needs_human`, `error`;
- техническую ошибку без секретов и персональных данных сверх необходимого.

## 5. Поток обработки вопроса

```text
1. Telegram присылает сообщение.
2. Бот извлекает chat_id и текст.
3. Система нормализует текст.
4. Поисковый сервис строит список кандидатов.
5. Confidence Gate проверяет порог и обязательные условия.
6а. При успешном совпадении отправляется готовый ответ из базы.
6б. При неуспешном совпадении отправляется fallback.
7. Результат записывается в журнал.
```

## 6. Конфигурация

Секреты и параметры окружения должны находиться вне репозитория:

- `TELEGRAM_BOT_TOKEN`;
- `KNOWLEDGE_BASE_PATH`;
- `CONFIDENCE_THRESHOLD`;
- `LOG_LEVEL`;
- параметры SQLite или внешнего хранилища;
- настройки webhook, если он будет использоваться.

В Git хранится только `.env.example` без реальных токенов.

## 7. Развёртывание

Для первой демонстрации используется polling на локальной машине или на небольшом сервере.

Для постоянной работы:

```text
Docker container
        |
        +--> Telegram Bot API
        +--> Knowledge Base volume
        +--> SQLite/PostgreSQL
        +--> Logs
```

Webhook и HTTPS добавляются после подтверждения MVP.

## 8. Наблюдаемость и контроль качества

Минимальный контроль:

- структурированные логи;
- количество обработанных вопросов;
- число fallback-ответов;
- частота ошибок Telegram API;
- список вопросов `needs_human`;
- тесты на обязательные и отрицательные сценарии.

## 9. Эволюция решения

### Версия 1 — MVP

YAML, контролируемый поиск, Telegram, SQLite, fallback.

### Версия 2 — рабочий пилот

Google Sheets или PostgreSQL как источник базы, администраторская перезагрузка, уведомления сервисного отдела.

### Версия 3 — масштабирование

Embeddings, векторное хранилище, CRM/HelpDesk, аналитика качества, роли пользователей и контроль версий статей.

## 10. Соответствие вакансии

Архитектура покрывает заявленные требования:

- база знаний и качество ответов — Knowledge Repository и Confidence Gate;
- сценарии диалогов — Message Handler и Escalation Service;
- интеграция мессенджера — Telegram Bot Adapter;
- поиск ошибок — Audit Logger и тесты;
- понятные инструкции — README и документация базы;
- развитие автоматизации — определённые этапы эволюции;
- объяснение бизнес-процесса — описанный поток от вопроса до результата.
