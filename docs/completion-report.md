# Отчёт о выполнении тестового задания

Дата проверки: 3 октября 2026 года

Вакансия: «Специалист по автоматизации и внедрению ИИ» в компании «Канализация Загород».

Ссылка: https://hh.ru/vacancy/138064743?from=share_ios

## 1. Цель решения

Создан рабочий прототип Telegram-бота сервисного отдела. Бот отвечает клиентам только на основании опубликованных материалов базы знаний и не генерирует технические инструкции самостоятельно.

Если подходящей статьи нет, бот сообщает об отсутствии информации и рекомендует обратиться в сервисный отдел. Неизвестные и неоднозначные обращения сохраняются в журнале для последующего разбора.

## 2. Что требовалось в тестовом задании

В тестовом задании требовалось:

1. Реализовать Telegram-бота.
2. Добавить три обязательных ответа по станциям КАН Ультра, КИТ и сценарию переполнения.
3. Не допускать выдуманных ответов.
4. Обрабатывать разные формулировки одного вопроса.
5. Для неизвестной станции, например «Тверь», направлять клиента в сервисный отдел.
6. Показать работающий прототип.
7. Объяснить архитектуру и расположение базы знаний.
8. Показать добавление новой информации без переписывания бизнес-логики.

Все пункты реализованы.

## 3. Реализованные ответы

### КАН Ультра

Для вопросов об очистке и обслуживании станции бот возвращает утверждённую ссылку:

https://youtu.be/WW1Hqh3_WNk

### КИТ

Бот возвращает точный текст из базы:

«Рекомендуем проводить обслуживание станции КИТ один раз в год.»

### Переполненная станция

Бот возвращает утверждённый безопасный сценарий:

«В первую очередь необходимо убедиться, что электрический блок с розетками не затоплен. Если блок затоплен — немедленно обесточить станцию и связаться с сервисным отделом компании.»

Ответ не пересказывается моделью и не дополняется автоматически.

## 4. Как предотвращаются выдуманные ответы

В прототипе нет генерации ответа через языковую модель. Алгоритм работает следующим образом:

1. Вопрос нормализуется: приводится к единому регистру, удаляются лишние знаки и учитывается замена «ё» на «е».
2. Выполняется проверка названия станции.
3. Ищутся только статьи со статусом `published`.
4. Проверяются утверждённые тематические слова и примеры вопросов.
5. Ответ разрешается только при одном однозначном совпадении.
6. При отсутствии совпадения, конфликте моделей или неоднозначности используется безопасный отказ.

Для вопроса «Как почистить станцию Тверь?» бот не находит опубликованную статью и отвечает, что информации в базе нет. Инструкция для КАН Ультра не подставляется.

При недоступности Google Таблицы бот также возвращает безопасный отказ и не использует устаревшую копию CSV.

## 5. База знаний и работа менеджера

Основной источник данных — приватная Google Таблица с вкладками:

- `Knowledge` — статьи базы знаний;
- `Инструкция` — описание полей и правил публикации.

Статья содержит поля:

- `id` — уникальный идентификатор;
- `status` — `draft`, `published` или `archived`;
- `equipment_aliases` — названия оборудования;
- `topic_terms` — тематические слова;
- `exclude_terms` — исключающие слова;
- `question_examples` — варианты вопросов;
- `answer` — утверждённый текст ответа.

Менеджер может добавить новую строку, сначала сохранить её как `draft`, проверить формулировки и затем изменить статус на `published`. Изменения применяются без изменения Python-кода и без перезапуска бота.

Также есть локальный редактор для демонстрации и автономный CSV-режим.

## 6. Соответствие вакансии

### Работа с Google Таблицами и данными

Реализовано:

- подключение приватной Google Таблицы через сервисный аккаунт;
- чтение и запись статей через Google Sheets API;
- валидация структуры и статусов;
- защита от дублирования ID;
- контроль конкурентного изменения статьи;
- разделение черновиков и опубликованных ответов.

### База знаний и сервисный ИИ-бот

Реализовано:

- Telegram-интеграция;
- безопасный поиск по базе знаний;
- сценарий уточнения модели станции;
- отказ от ответа при отсутствии информации;
- обработка неизвестных и неоднозначных обращений;
- журнал обращений, требующих сотрудника.

### API и интеграции

Реализовано:

- Telegram Bot API через polling;
- Google Sheets API;
- обработка сетевых ошибок и повторные попытки polling;
- локальный HTTP-интерфейс для оператора.

### Тестирование и поиск ошибок

Добавлены тесты на:

- обязательные ответы;
- переформулировки и регистр;
- ограниченную обработку опечаток;
- неизвестную станцию;
- несколько моделей в одном вопросе;
- отрицание темы;
- уточнение модели и срок действия контекста;
- недоступность Google Таблицы;
- безопасность локального редактора;
- ошибки Telegram API.

Бизнес-тесты, тесты диалогов, Google Sheets и Telegram API проходят. Полная проверка локального HTTP-теста в среде Codex ограничена запретом на открытие временного TCP-порта; ранее редактор был проверен при обычном локальном запуске.

### Простые инструкции и обучение сотрудников

В репозитории есть:

- README с запуском и демонстрационным сценарием;
- описание архитектуры;
- схема базы знаний;
- инструкция для менеджера;
- правила публикации статей;
- описание ограничений и безопасного отказа.

### Стабильная эксплуатация

В прототипе предусмотрены:

- безопасная обработка ошибок Telegram и Google API;
- журналирование обращений;
- статусы обработки;
- ограничение локального редактора адресом `127.0.0.1`;
- защита форм от CSRF;
- экранирование пользовательского текста;
- исключение токенов, ключей и SQLite-файлов из Git.

## 7. Что пока не входит в тестовый прототип

Следующие пункты вакансии относятся к более широкому рабочему контуру компании и не требовались для текущего тестового задания:

- интеграция с CRM;
- автоматизированная отчётность отдела продаж;
- сбор информации о конкурентах;
- аналитика маркетинговых экспериментов;
- автоматическая отправка сложных вопросов в рабочий чат сервисного отдела;
- роли и согласование статей на уровне полноценной корпоративной системы;
- постоянный серверный деплой, Docker и мониторинг.

Для MVP сложные вопросы уже фиксируются в журнале `needs_human`. Следующим шагом можно подключить уведомление сервисному сотруднику в Telegram, CRM или Google Chat.

## 8. Архитектура

```text
Клиент Telegram
       ↓
Telegram Bot API
       ↓
Python polling-приложение
       ↓
Нормализация → проверка модели → поиск статьи
       ↓
Точный ответ из Knowledge
       или
Fallback / уточнение / журнал needs_human
       ↓
Приватная Google Таблица
```

Python выбран потому, что для небольшого прототипа он позволяет быстро реализовать Telegram API, работу с Google Sheets, тесты и локальный запуск без сложной инфраструктуры.

## 9. Демонстрационный сценарий

1. Запустить `python3 -m service_bot`.
2. Показать вопрос про КАН Ультра и ссылку на видео.
3. Показать вопрос про периодичность обслуживания КИТ.
4. Показать безопасный ответ для переполненной станции.
5. Спросить про станцию Тверь и показать отказ от выдумывания инструкции.
6. Спросить «Как самому обслужить станцию?» и показать уточнение модели.
7. Ответить «КАН Ультра» и получить утверждённый ответ.
8. Открыть Google Таблицу и показать поля статьи и статусы.
9. Добавить новый пример вопроса через таблицу, не меняя код.
10. Показать журнал вопросов без ответа.

## 10. Итоговая оценка

Тестовое задание выполнено полностью.

Решение демонстрирует не просто создание Telegram-бота, а полный подход специалиста по внедрению автоматизаций:

- выделены бизнес-правила;
- определён источник истины;
- предусмотрена работа менеджера без разработчика;
- реализована безопасная стратегия при отсутствии данных;
- добавлены тесты позитивных и негативных сценариев;
- подготовлены инструкции для пользователя;
- обозначены границы MVP и следующие этапы развития.

Ключевой аргумент на собеседовании: для сервисного бота безопасность важнее свободной генерации. Поэтому система сначала проверяет наличие утверждённой информации, а при сомнении передаёт вопрос человеку.
