# План реализации и статус прототипа

Фазы 0–7 ниже реализованы. Основной источник знаний — приватная Google Таблица; автономный CSV служит отдельным режимом демонстрации, а не резервной подменой при сбое Google. Для Google-режима нужны зависимости из `requirements-google.txt`.

## Фаза 0. Согласование архитектуры

Результаты:

- утверждены границы MVP;
- согласован формат базы знаний;
- определён текст fallback-сообщения;
- определены условия однозначного совпадения;
- согласована схема демонстрации.

## Фаза 1. Каркас проекта

Результаты:

- создан Python-проект;
- выбран Python со стандартной библиотекой для Telegram и локального режима; для Google Sheets добавлены официальные библиотеки Google;
- добавлены конфигурация и `.env.example`;
- настроено логирование;
- подготовлена структура каталогов.

## Фаза 2. Telegram-интеграция

Результаты:

- бот принимает текстовые сообщения;
- работают `/start` и `/help`;
- ошибки отправки фиксируются в логах.

## Фаза 3. База знаний

Результаты:

- добавлены три обязательные статьи;
- база загружается независимо от Telegram-слоя;
- добавлены правила валидации структуры;
- описан процесс добавления новой статьи.

## Фаза 4. Поиск и проверка совпадения

Результаты:

- реализована нормализация вопроса;
- реализован отбор кандидатов;
- ответ разрешён только при одной подходящей статье;
- добавлена проверка сущности станции;
- добавлена ограниченная обработка одной опечатки в длинном тематическом слове;
- при отсутствии модели запрашивается уточнение, при нескольких моделях ответ не выбирается;
- неоднозначные вопросы не получают случайный ответ.

## Фаза 5. Ответы и эскалация

Результаты:

- бот возвращает только готовый ответ из статьи;
- неизвестные вопросы получают fallback, а неполный вопрос о модели — уточнение;
- вопросы сохраняются со статусом `needs_human`;
- подготовлена точка интеграции с сервисным отделом.

## Фаза 6. Тестирование

Обязательные тестовые группы:

1. Точные формулировки.
2. Переформулированные вопросы.
3. Вопросы с одной опечаткой и разным регистром (покрыты тестами).
4. Неизвестная станция.
5. Общий и неоднозначный вопрос.
6. Проверка неизменности официального ответа.
7. Ошибки загрузки базы.
8. Ошибки Telegram API.
9. Контекст уточнения модели и его истечение.
10. Несколько моделей и отрицание темы в одном вопросе.

## Фаза 7. Документация и демонстрация

Результаты:

- README с запуском;
- архитектурная схема;
- описание базы знаний;
- сценарий тестирования и показа в README;
- инструкция добавления статьи;
- live-демонстрация Telegram-бота;
- объяснение защиты от выдуманных ответов.

## Фаза 8. Подготовка к пилоту

После успешного MVP:

- при необходимости перенести базу из Google Sheets в PostgreSQL или специализированную CMS;
- добавить уведомления сервисному отделу;
- настроить Docker-развёртывание;
- добавить метрики качества;
- согласовать процесс проверки новых статей;
- определить SLA и ответственных сотрудников.

## Критерии приёмки MVP

- три обязательных ответа выдаются корректно;
- разные формулировки находят одну статью;
- вопрос про Тверь не получает выдуманную инструкцию;
- неизвестный вопрос попадает в журнал;
- база знаний редактируется отдельно от бизнес-логики;
- проект запускается по README;
- тесты покрывают позитивные и негативные сценарии.
